# موتور پژوهش و شبیه‌سازی بازار والکس

این پروژه دادهٔ عمومی بازارهای تومانی والکس را دریافت می‌کند، سیگنال و حدود ریسک را بررسی می‌کند و وضعیت یک سبد آزمایشی را در داشبورد فارسی نشان می‌دهد. کد پژوهش تاریخی، حسابداری کارمزد، دفتر پایدار SQLite و ابزارهای عملیاتی نیز در مخزن هستند. راه‌اندازی این صفحه فقط شبیه‌سازی با پول مجازی است و کلید حساب صرافی لازم ندارد.

بستهٔ حاضر نسخهٔ اصلاح‌شدهٔ حسابداری کارمزد است. گزارش تغییرات و آزمون‌های مربوط در [FEE_FIX_FA.md](FEE_FIX_FA.md) آمده است. اطلاعات حساب، کلید دسترسی، دفتر معاملات خصوصی و گزارش استقرار شخصی در این مخزن قرار ندارند.

## ساختار پروژه

| مسیر | کاربرد |
| --- | --- |
| `wallex_engine/cloud.py` | اجرای پیوستهٔ عمومی و آزمایشی، دریافت سابقه، خبر و ذخیرهٔ وضعیت |
| `wallex_engine/engine.py` و `runtime.py` | سیگنال، اندازهٔ موقعیت، کنترل ریسک و چرخهٔ جلسه |
| `wallex_engine/adaptive_risk.py` | کاهش ریسک در حالت آزمایشی بر اساس نوسان، بازار و کیفیت پوشش خبر |
| `wallex_engine/execution.py` و `fees.py` | اعتبارسنجی اجراها، کارمزد و بازیابی سفارش‌های ثبت‌شده |
| `wallex_engine/session_limits.py` | زمان پایان مطلق و حدود جلسه، با حفظ وضعیت پس از بازیابی |

| `deploy/paper-seed/` | تنظیمات، مدل و دادهٔ اولیهٔ شبیه‌سازی |

| `tests/` | آزمون‌های مهندسی با داده‌ها و پاسخ‌های ساختگی |

## مدل و حدود شواهد

مدل همراه مخزن `research_only=true` و `prospective_validated=false` دارد و فیلد `fit` آن `null` است. سیاست فعال این نمونه مجموعه‌ای ثابت از قواعد تکنیکی است؛ این بسته مدرک آموزش یک مدل یادگیری ماشین یا تصمیم‌گیری یک مدل زبانی نیست. وجود پیاده‌سازی‌های یادگیری در پروژه به معنی فعال بودن آن‌ها در مدل همراه نیست.

عامل تطبیقی ریسک فقط می‌تواند اندازهٔ ورود آزمایشی را کاهش دهد یا ورود را مسدود کند؛ سقف‌های پایه را افزایش نمی‌دهد و مسیر خروج را مسدود نمی‌کند. دادهٔ ناقص یا قدیمی و پوشش خبری ضعیف می‌توانند باعث کاهش ریسک شوند. برچسب‌های کلیدواژه‌ای تیترها، تأیید وقوع رویداد یا پیش‌بینی قابل اتکای قیمت نیستند.

دادهٔ اولیه برای هر یک از پنج بازار، ۷۲۱ کندل یک‌ساعته دارد. این مقدار سابقهٔ اولیهٔ سیاست همراه است و دورهٔ مستقلی برای اثبات سودآوری باقی نمی‌گذارد. موفقیت آزمون حسابداری یا اجرای یک نمونهٔ مصنوعی، نتیجهٔ بک‌تست بازار نیست. برای ارزیابی عملکرد، دورهٔ مستقل کافی، هزینه‌ها، دادهٔ قابل دسترس در زمان تصمیم و هویت ثابت سیاست باید جداگانه ثبت شوند. مسیر بک‌تست پایه نیز لزوماً سیاست تطبیقی اجرای `cloud` را بازسازی نمی‌کند.

## نصب محلی

فرمان‌ها را در ریشهٔ مخزن اجرا کنید. نسخهٔ بررسی‌شده از Python 3.12 و Node.js برای آزمون رابط استفاده کرده است. وابستگی‌های پایتون در `requirements.txt` ثابت شده‌اند.

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
```

برای جلوگیری از مخلوط شدن دادهٔ اجرا با فایل‌های نسخه، یک کپی محلی از seed بسازید. این مرحله فقط یک‌بار برای این پوشهٔ آزمایش است؛ اگر `.local/seed` وجود داشته باشد، فرمان آن را بازنویسی نمی‌کند.

```bash
.venv/bin/python - <<'PY'
from pathlib import Path
import shutil

Path('.local/state').mkdir(parents=True, exist_ok=True)
shutil.copytree('deploy/paper-seed', '.local/seed')
PY
```

تاریخ‌های بسته ثابت و مربوط به نمونهٔ اولیه‌اند. `session-plan.json` همراه، پایان را روی `2026-10-26T23:59:59+03:30` قرار داده است؛ این تاریخ با هر اجرا جلو نمی‌رود. پس از آن، جلسهٔ تازه با همین طرح شروع نمی‌شود. اعتبار مدل همراه نیز تا `2026-11-21T10:00:00Z` است و بیرون از بازهٔ اعتبار، پیش‌بینی فعال تولید نمی‌کند.

برای آزمایش جدید، قبل از اولین اجرا زمان پایان را در کپی `.local/seed/session-plan.json` آگاهانه انتخاب کنید؛ باید در آینده و حداکثر هفت روز بعد باشد. تغییر تاریخ طرح، اعتبار مدل را تمدید نمی‌کند. برای دوره‌ای بیرون از اعتبار مدل، به مدل و دادهٔ بررسی‌شدهٔ مناسب آن دوره نیاز دارید. فایل‌های `deploy/` مرجع نسخه هستند و بهتر است دست‌نخورده بمانند.

## اجرای شبیه‌سازی و داشبورد

در ترمینال اول، worker عمومی را اجرا کنید:

```bash
APP_MODE=shadow \
DATA_DIR="$PWD/.local/state/paper-monday" \
SEED_DIR="$PWD/.local/seed" \
WORKER_BIND_HOST=127.0.0.1 PORT=8732 \
.venv/bin/python -B -m wallex_engine.cloud
```

این worker فقط `shadow` را می‌پذیرد و از کلاینت عمومی بازار استفاده می‌کند. برای دادهٔ بازار و منابع خبر به اینترنت نیاز دارد. شروع کار به دریافت سابقهٔ کامل و پیوسته وابسته است؛ کندل گمشده ساخته نمی‌شود. نبود سابقهٔ کافی، خبر قابل استفاده یا سیگنال مناسب ممکن است به انتظار یا صفر معامله منجر شود. آماده‌بودن پردازش الزاماً به معنی وجود فرصت ورود نیست.

در ترمینال دوم، از همان ریشهٔ مخزن داشبورد را اجرا کنید:

```bash
PAPER_STATE_ROOT="$PWD/.local/state" \
SEED_DIR="$PWD/.local/seed" \
PAPER_WORKER_PORT=8732 PORT=8733 \
.venv/bin/python -B -m observer.paper_server
```

نشانی داشبورد محلی `http://127.0.0.1:8733/` است. رمز آن هنگام اولین اجرای داشبورد با دسترسی محدود در `.local/state/dashboard-token` ساخته می‌شود. برای ورود، این فایل را فقط روی رایانهٔ خود بخوانید؛ رمز داشبورد کلید صرافی نیست و نباید به مخزن اضافه شود.

```bash
cat .local/state/dashboard-token
curl -i http://127.0.0.1:8732/readyz
```

هر دو سرویس این نمونه فقط روی loopback گوش می‌دهند. پاسخ `200` از `/readyz` همراه `ready=true` یعنی worker ضربان تازه دارد؛ پس از پایان جلسه worker خارج می‌شود و ممکن است این نشانی دیگر پاسخ ندهد. داشبورد وضعیت آخر ذخیره‌شده را با برچسب شبیه‌سازی نشان می‌دهد.

برای توقف دستی از `Ctrl+C` در هر ترمینال استفاده کنید. اجرای دوباره با همان مسیرها، دفتر همان آزمایش را باز می‌کند و زمان پایان یا پول مجازی را بازنشانی نمی‌کند. تغییر کد، مدل یا تنظیمات یک دفتر موجود عمداً می‌تواند مانع ادامه شود؛ برای آزمایش مستقل از پوشهٔ تازه و تنظیمات معتبر استفاده کنید و دفتر قبلی را حفظ کنید.

## آزمون‌ها

```bash
.venv/bin/python -B -m unittest discover -s tests -v
node tests/test_observer_frontend.js
```

در بررسی نسخهٔ مبنا، ۱۳۲ آزمون پایتون و آزمون رابط Node.js موفق بودند. آزمون‌های اجرای سفارش از پاسخ‌های ساختگی استفاده می‌کنند؛ موفقیت آن‌ها اثبات عملکرد صرافی، سودآوری یا نتیجهٔ حساب واقعی نیست. برای یک نمونهٔ مصنوعی مستقل از بازار نیز فرمان زیر موجود است؛ این فرمان مدل و تنظیمات پیش‌فرض CLI را به کار می‌برد و بازتولید سیاست seed نیست:

```bash
.venv/bin/python -B -m wallex_engine demo --out .local/synthetic-demo
```

## دامنهٔ حساب و کارمزد

مسیر عملیاتی `operator_trial` در کد، `main_spot` است. این مسیر معادل کیف پول اعتباری، مارجین یا حساب مسابقه نیست و نباید به عنوان مسیر چنین حساب‌هایی معرفی شود. مسیر عمومی اجرای واقعی نیز بررسی‌های جداگانهٔ تنظیمات و حساب دارد. دستورهای این راهنما هیچ‌یک از مسیرهای اجرای واقعی را فعال نمی‌کنند.

دارایی کارمزد از `fills[].feeAsset` واقعی خوانده می‌شود. کارمزد رمزارزی و تومانی به روش متفاوت ثبت می‌شوند و دوباره از مانده کسر نمی‌شوند. نرخ‌های Maker/Taker نقش نقدشوندگی هستند و به معنی خرید/فروش نیستند. جزئیات و محدودیت باقی‌ماندهٔ دقت مقدار و ماندهٔ خرد در [گزارش اصلاح کارمزد](FEE_FIX_FA.md)، [مستند رسمی نرخ کارمزد](https://developers.wallex.ir/docs/basic-services-account-fee) و [مستند جزئیات سفارش](https://developers.wallex.ir/docs/spot-single-order-detail) آمده است.

## هویت نسخه و تحویل

هش موتور، از نام و محتوای مرتب‌شدهٔ فایل‌های مستقیم `wallex_engine/*.py` محاسبه می‌شود؛ هش کل مخزن نیست:

```text
59be964cc3730cc67ce36626c8ab2cb5a14883b9de7fc3c682da1980a4a716a9
```

هش SHA-256 هر دو فایل مدل همراه:

```text
13fe05459e702a1488f36734251a740f4da061132cb873cbba16233e6e8115cb
```

بررسی محلی این دو شناسه:

```bash
.venv/bin/python -B - <<'PY'
from pathlib import Path
import hashlib
from wallex_engine.audit import source_hash

print('engine:', source_hash())
for path in (Path('deploy/seed/model.json'), Path('deploy/paper-seed/model.json')):
    print(path, hashlib.sha256(path.read_bytes()).hexdigest())
PY
```

مستندات این انتشار عمومی جایگزین شرح استقرار خصوصی شده‌اند؛ کد موتور و مدل همراه همان هویت بالا را دارند. اطلاعات بسته در `fee-release.json` ثبت شده است. این فایل و هش‌ها شاهد هویت و آزمون نسخه‌اند، نه تأیید وضعیت فعلی هیچ سرور یا حسابی. دادهٔ اجرا، کلیدها و فایل‌های محلی از طریق `.gitignore` کنار گذاشته شده‌اند؛ پیش از هر commit، فهرست فایل‌های آمادهٔ ثبت را نیز بررسی کنید.
